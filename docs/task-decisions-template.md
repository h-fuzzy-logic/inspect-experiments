# Task decisions template

The choices you make when you design and run an Inspect task. Copy this file into a task's folder, such as `tasks/<name>/DECISIONS.md`, and fill in the **Choice and reason** column as you go.

Two kinds of entries are easy to miss:

- **Defaults are choices too.** If you keep an Inspect default, such as `react()`'s default prompt, write "default" and why it's fine.
- **"Not yet" is a valid choice.** Write it down with the reason, so a reviewer knows it was considered.

## Design Time

Decisions made while building the task, before any real model runs.

### Purpose and scope

| Decision | Options to consider | Choice and reason |
|---|---|---|
| What the task measures | One capability, stated in a sentence | |
| What it doesn't measure | Nearby skills a reader might assume it covers | |
| Target difficulty | Expected pass rate for the models you'll test. A task every model aces can't rank them | |
| Target human time | Minutes, hours, or days for a skilled person | |
| Realism | Toy problem, realistic slice of a real system, or a full system | |
| Contamination risk | Could the problem or its answer be in training data? | |

### Samples

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Number of samples | Enough for the stderr you need. One sample can only pass or fail | |
| What varies between samples | Error type, difficulty, domain, size | |
| Difficulty spread | All similar, or a range from easy to hard | |
| Where samples come from | Hand-written, generated by a script, adapted from real code | |
| Sample IDs and metadata | Names that describe the sample; metadata to break results down by | |
| Reference solution per sample | Yes or no. Needed to prove each sample is solvable | |
| Hidden inputs | Inputs the agent never sees, used only to score, so a solution can't be fitted to visible data | |
| How samples are stored | One folder per sample, a JSON or CSV file, or generated at load time | |

### Environment (sandbox)

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Sandbox type | None, Docker, or Kubernetes | |
| Base image | Which image, and whether it's pinned by digest | |
| Software installed | Only what the task needs | |
| User and permissions | Root or a non-root user; which files the agent can read and write | |
| Network access | None, or a limited allowlist | |
| Files copied in | Which files enter the sandbox, and when (image build or sample start) | |
| Resources | CPU, memory, disk | |
| Services | Databases, web servers, or other containers the task needs | |
| Reproducibility | Pinned versions, fixed seeds, no dependence on the current date or the network | |

### Answer protection

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Where answers live | Host only, scorer-only files, or a separate container | |
| Guards against leaks | `.dockerignore`, no `COPY` of task files, permissions on scorer files | |
| Canary string | Whether to add one, and in which files | |
| Public or private task | Whether the samples and answers go in a public repo | |

### Prompts

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Task instructions | What the agent is told: the goal, the files, what counts as done | |
| Level of detail | Just the goal, or hints about where to look and how | |
| Constraints stated | Rules the scorer enforces, such as "change as little as possible." Unstated rules make failures unfair | |
| System prompt | The agent's default prompt, or a custom one | |
| Submit instructions | Whether and how the agent must submit | |
| Prompt variants | One prompt, or several to measure sensitivity to wording | |

### Agent (solver)

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Agent | `react()`, another built-in agent, or a custom solver | |
| Tools | `bash()`, `python()`, `text_editor()`, web tools, custom tools | |
| Tool timeouts | How long one tool call may run | |
| Submission | Whether the agent must call `submit()`, and whether it gets more than one attempt | |
| Test solvers | A reference solver and a do-nothing solver, to test the scorer without a model | |

### Limits

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Message limit | Maximum messages per sample | |
| Token limit | Maximum tokens per sample | |
| Time limit | Wall-clock time per sample | |
| Working limit | Time per sample, not counting waits such as rate limits | |
| Where limits are set | In the task, so every run uses them, or on the command line | |
| What a limit hit means | Scored on the end state, or counted as a fail | |

### Scorer logic

| Decision | Options to consider | Choice and reason |
|---|---|---|
| What's scored | The final state of the environment, the submitted answer, or both | |
| How correctness is checked | Exact match, run the code, compare with a reference, tests, a model grader | |
| Shortcut checks | Rules that stop a wrong solution from passing, such as a limit on lines changed | |
| Score values | Pass or fail, partial credit, or a numeric score | |
| Partial credit | If used: which steps earn credit, and how much each is worth | |
| Recorded reasons | What's saved with each score: verdicts, explanations, metadata | |
| Metrics | Accuracy, stderr, means by group | |
| Where the scorer runs | On the host, in the sandbox, or both | |
| Scorer timeouts | How long the scorer waits on the agent's code | |
| Model graders | If a model grades: which model, its rubric, and how the grader is checked | |

### Tests

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Sample checks | Each sample is broken, each reference fix works, files are consistent | |
| Positive controls | Correct solutions that must pass, including other valid solutions | |
| Negative controls | Wrong solutions that must fail, each for the right reason | |
| Shortcut tests | One test per known shortcut. Open ones marked `xfail` until fixed | |
| Environment tests | Permissions, installed tools, network access | |
| What each test asserts | The score only, or the score and the reason for it | |
| When tests run | By hand, before each real run, or in CI | |

### Build-time QA

| Decision | Options to consider | Choice and reason |
|---|---|---|
| How much QA | A quick check, or a full pass with a written log | |
| Spec review | Is anything ambiguous, or unstated but scored? | |
| Red-teaming the scorer | List wrong solutions that could pass, and test each | |
| Leak audit | Can the agent find the answer anywhere in the sandbox? | |
| Solvability check | Run the reference solution in the real sandbox | |
| QA log | Where findings go, and their fields: type, how found, fix, how verified | |
| When QA is done | The point at which the task is ready for real runs | |

### Human baseline

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Whether to baseline | Yes, estimate only, or not yet | |
| Who | The author, who knows the answers, or someone new to the task | |
| How | Inspect's human agent in the same sandbox, or by hand | |
| What's recorded | Time, pass or fail, notes on what was hard | |

### Reporting plan

| Decision | Options to consider | Choice and reason |
|---|---|---|
| What's reported | Pass rates, stderr or confidence intervals, limit hits, tokens, time | |
| Figures | Which charts, and how they're generated | |
| Mock or placeholder data | Whether to show it, and how it's labeled | |
| Versioning | When a change gets a new task or scorer version, and how versions are compared | |

## Run Time

Decisions made each time the task runs.

### Where to run

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Location | Local machine, a codespace, or other cloud resources | |
| What runs where | Mock-model and reference runs locally; real models in the cloud | |
| API keys | Where they're stored, and who can use them | |
| Code version | How the run machine gets the right commit, and how you check it | |

### Models

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Which models | Providers and model versions | |
| Why these models | Range of capability, cost, availability | |
| Generation settings | Temperature, reasoning effort, max tokens, or the provider's defaults | |
| Free or paid tier | Rate limits, and whether the provider may train on the data | |
| Mock model | `mockllm/model` for testing the pipeline | |

### Run size

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Epochs | Runs per sample. More epochs measure consistency | |
| Samples per run | All, a subset (`--limit`), or one (`--sample-id`) | |
| Smoke test | A small run before the full one | |
| Repeat evals | How many full evals per model, and when | |

### Concurrency and reliability

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Concurrent model calls | `--max-connections`, within the provider's rate limits | |
| Concurrent sandboxes | `--max-sandboxes`, within the machine's CPU and memory | |
| Retries | `--max-retries` and `--attempt-timeout` for slow or failed model calls | |
| Errors | Whether a sample error stops the eval (`--fail-on-error`) | |
| Limits set at run time | `--time-limit`, `--message-limit`, `--token-limit`, if not set in the task | |

### Cost

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Budget | A spend limit per eval and overall | |
| Estimate | Tokens per run from a smoke test, times runs | |
| Cost controls | Fewer epochs, cheaper models, caching, smaller samples | |

### Before each run

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Checks | Tests pass, reference solution scores 1, do-nothing scores 0 | |
| Code check | The run machine is on the expected commit with no uncommitted changes | |
| Environment check | Docker running, enough disk, keys set | |
| Run record | Where you note the command, commit, date, and why the run was done | |

### Run-time QA

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Which transcripts to read | All, all failures, a sample of passes, or all limit hits | |
| What to look for | Shortcuts, environment problems, unclear instructions, scorer mistakes | |
| Passes to check | Whether to read some passes to catch false passes | |
| Failure review | Classify each failure: the model's fault or the task's | |
| Verdict counts | Whether the reasons for passes and fails match what you expected | |
| Limit hits and errors | Whether they come from the model or the setup | |
| Flakiness | Do repeat runs of the same sample disagree, and why? | |
| What triggers a fix | Which findings change the task, and whether earlier results are rerun | |

### Results

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Which logs count | Latest per model, all, or ones from a set commit | |
| Where logs are kept | Local only, shared storage, or published | |
| How results are built | Scripts that read the logs, or by hand | |
| What's published | Tables, figures, transcripts, and which logs | |
| Comparing runs | Only runs with the same task, scorer, and settings | |
