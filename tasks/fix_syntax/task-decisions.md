# fix_syntax: task decisions

The choices made in designing and running this task, filled in from the [task decisions template](../../docs/task-decisions-template.md). Entries marked **Open** haven't been decided yet. Entries marked **Default** keep Inspect's default on purpose.

For the details behind these choices, see [README.md](README.md), [RESULTS.md](RESULTS.md), and [QA.md](QA.md).

## Design Time

### Purpose and scope

| Decision | Options to consider | Choice and reason |
|---|---|---|
| What the task measures | One capability, stated in a sentence | Whether an agent can run a broken script, read the syntax error, find the line at fault, and fix it with a small edit |
| What it doesn't measure | Nearby skills a reader might assume it covers | General programming ability, logic bugs, multi-file debugging, or long tasks |
| Target difficulty | Expected pass rate for the models you'll test | Easy on purpose. It's a warm-up for practicing the task-building method, not for ranking models |
| Target human time | Minutes, hours, or days for a skilled person | A few minutes per sample. Not measured yet: the human times in the baseline chart are mock |
| Realism | Toy problem, realistic slice of a real system, or a full system | Toy problem: short standalone scripts, each with one planted error |
| Contamination risk | Could the problem or its answer be in training data? | High for the kind of error: common syntax errors are frequent in training data, so scores may partly reflect familiarity. The scripts are new, but an AI assistant wrote them, so they follow common patterns. The models tested are from the same family as the one that wrote them, which may make the samples easier for them |

### Samples

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Number of samples | Enough for the stderr you need | 8. Enough to show the workflow and catch large differences, not to separate similar models. See [Why several samples](README.md#why-several-samples) |
| What varies between samples | Error type, difficulty, domain, size | Error type: each sample has a different kind of syntax error. Each script has a different everyday topic |
| Difficulty spread | All similar, or a range from easy to hard | All similar and easy. Every fix changes exactly one line |
| Where samples come from | Hand-written, generated by a script, adapted from real code | Written by an AI coding assistant (Claude Code), to the author's spec: one common syntax error per sample, each fixed by a one-line change. The sample tests check each one |
| Sample IDs and metadata | Names that describe the sample; metadata to break results down by | IDs name the error, such as `missing_colon_if`. Metadata holds the script path and a description of the error, used as chart row labels |
| Reference solution per sample | Yes or no | Yes: `fixed.py` for each sample, plus `expected.txt` with the exact output |
| Hidden inputs | Inputs the agent never sees, used only to score | Not yet. Planned, to close shortcuts QA-004, QA-009, and QA-010 |
| How samples are stored | One folder per sample, a JSON or CSV file, or generated at load time | One folder per sample, listed in `samples/samples.json`. A test checks the folders and the list match |

### Environment (sandbox)

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Sandbox type | None, Docker, or Kubernetes | Docker. One container per sample |
| Base image | Which image, and whether it's pinned by digest | `python:3.12-slim`. Not pinned yet, so a rerun may get a newer image. Pinning is listed under [Could be better](RESULTS.md#could-be-better) |
| Software installed | Only what the task needs | Only what the base image has: Python and a shell |
| User and permissions | Root or a non-root user | Non-root user `agent`, who owns `/workspace`, so the agent can edit files but not change the system (QA-001) |
| Network access | None, or a limited allowlist | None (`network_mode: none`, Inspect's default for a generated compose file). The task needs no network |
| Files copied in | Which files enter the sandbox, and when | Only the sample's `broken.py`, copied in when the sample starts. The image has no task files |
| Resources | CPU, memory, disk | **Default.** The scripts are tiny |
| Services | Other containers the task needs | None |
| Reproducibility | Pinned versions, fixed seeds, no dependence on date or network | No network, no randomness, fixed sample files. The image isn't pinned yet |

### Answer protection

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Where answers live | Host only, scorer-only files, or a separate container | Host only. `fixed.py` and `expected.txt` never enter the sandbox |
| Guards against leaks | `.dockerignore`, no `COPY` of task files, permissions | `.dockerignore` hides the whole task folder from the build, and the Dockerfile has no `COPY` (QA-003) |
| Canary string | Whether to add one, and in which files | Yes. It's in `RESULTS.md` and `QA.md`, but not yet in the sample files that hold the answers (QA-008, open) |
| Public or private task | Whether samples and answers go in a public repo | Public: this is a portfolio repo. Acceptable for a warm-up task |

### Prompts

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Task instructions | The goal, the files, what counts as done | One prompt template, with the script path filled in per sample. It names the file, the goal (runs successfully), and two constraints |
| Level of detail | Just the goal, or hints | Goal only. It doesn't say where the error is or what kind it is |
| Constraints stated | Rules the scorer enforces | "Change as little as possible, and don't change what the script prints." These match the scorer's two checks |
| System prompt | The agent's default prompt, or a custom one | **Default:** `react()`'s default prompt. See [What the agent sees](README.md#what-the-agent-sees) |
| Submit instructions | Whether and how the agent must submit | The prompt ends "When you're done, submit." The default system prompt also names the `submit()` tool |
| Prompt variants | One prompt, or several | One. **Open:** a minimal-prompt variant to test sensitivity to the system prompt |

### Agent (solver)

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Agent | `react()`, another built-in agent, or a custom solver | `react()`, Inspect's standard agent loop |
| Tools | `bash()`, `python()`, `text_editor()`, and others | `bash()` only. Enough to run, read, and edit a script |
| Tool timeouts | How long one tool call may run | 60 seconds per `bash()` call |
| Submission | Whether the agent must submit, and how many attempts | **Default:** one `submit()`. The scorer checks the files, not the submission, so a run that never submits can still pass |
| Test solvers | A reference solver and a do-nothing solver | Both, chosen with `-T solution=reference` and `-T solution=none` |

### Limits

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Message limit | Maximum messages per sample | 30. A one-line fix needs only a few turns, so this stops a stuck agent without cutting off a slow one |
| Token limit | Maximum tokens per sample | None |
| Time limit | Wall-clock time per sample | 600 seconds |
| Working limit | Time not counting waits | None |
| Where limits are set | In the task, or on the command line | Message limit in the task. Time limit only on the command line. Moving it into the task is listed under [Could be better](RESULTS.md#could-be-better) |
| What a limit hit means | Scored on the end state, or a fail | Scored on the end state. A correct fix cut off by a limit still passes. Limit hits are counted separately (QA-005) |

### Scorer logic

| Decision | Options to consider | Choice and reason |
|---|---|---|
| What's scored | The final state, the submitted answer, or both | The final state of the script in the sandbox |
| How correctness is checked | Exact match, run the code, a reference, tests, a model grader | Run the script. It must exit cleanly and print exactly `expected.txt`, apart from surrounding whitespace |
| Shortcut checks | Rules that stop a wrong solution from passing | At most 3 lines changed from `broken.py` (QA-002). Open gaps: QA-004, QA-009 to QA-011 |
| Score values | Pass or fail, partial credit, or a numeric score | Pass or fail (`C` or `I`) |
| Partial credit | Which steps earn credit | None. A one-line fix has no useful steps to credit |
| Recorded reasons | Verdicts, explanations, metadata | A `Verdict` (`fixed`, `still_broken`, `wrong_output`, `rewritten`, `missing`, `timed_out`), the number of lines changed, and an explanation |
| Metrics | Accuracy, stderr, means by group | Accuracy and stderr. Per-sample pass rates and verdict counts are computed from the logs afterward |
| Where the scorer runs | On the host, in the sandbox, or both | On the host. It runs the script and reads the file in the sandbox, and compares with files on the host |
| Scorer timeouts | How long the scorer waits on the agent's code | 30 seconds for running the script. A hang scores `timed_out` |
| Model graders | Which model, its rubric, how it's checked | None needed. Every check is exact |

### Tests

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Sample checks | Each sample is broken, each fix works, files are consistent | Yes. Every `broken.py` has a syntax error, every `fixed.py` prints `expected.txt`, they differ by one line, and every folder is listed |
| Positive controls | Correct solutions that must pass | All 8 reference fixes, another valid one-line fix, trailing whitespace, a separate `if` in place of `elif` |
| Negative controls | Wrong solutions that must fail | All 8 broken scripts, wrong output, an error exit, a hardcoded `print()`, a deleted script |
| Shortcut tests | One test per known shortcut, `xfail` if open | One per shortcut. 4 open ones are `xfail(strict=True)`, so pytest flags them when they're fixed |
| Environment tests | Permissions, tools, network | The `agent` user can edit every script |
| What each test asserts | The score only, or the score and its reason | Both: each test checks the verdict, so a test can't pass for the wrong reason |
| When tests run | By hand, before each real run, or in CI | By hand. CI is **Open** |

### Solvability checks

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Reference solution | Write the intended solution and run the scorer on it | Yes. Each sample has a `fixed.py`. `test_all_reference_fixes_pass` scores every one in the real sandbox, and `-T solution=reference` does the same from the command line |
| Pre-fix failure check | Confirm every sample fails before any fix | Yes. `test_sample_files_are_consistent` checks each `broken.py` has a syntax error, and `test_all_broken_scripts_fail` checks each scores `still_broken` in the sandbox |
| Clean-room dry run | Solve it in the sandbox, as the agent's user, with only the agent's tools | Partly. `test_agent_user_can_edit_every_script` edits every script with `sed -i` as the `agent` user. A full solve by hand in the sandbox is **Open**; the human baseline would cover it |
| Independent baseline | Someone other than the author solves it from the instructions alone | **Open.** The planned baseliner is the author |
| Alternative solution | A second valid approach must also pass | Yes. `test_other_one_line_fix_passes` and `test_separate_if_instead_of_elif_passes` |
| Limits check | Time the reference solution against the task's limits | Not as a timed check. Each fix is one line, and the limits are set well above what that needs |
| Repeat builds | Rebuild and score the reference solution several times | Not done on purpose. The samples are fixed files with no randomness, so there's little to vary. **Open** |
| Milestone checks | Check each intermediate goal can be reached | Not applicable: each sample is a single step |

### Spec review

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Second reading | List every plausible interpretation of each sentence | **Open** |
| Spec-to-scorer traceability | Map every scorer check to a sentence, and every sentence to a check | Yes, below. "Fix the error" is only checked through its effects, which is where the open shortcuts come from |
| Assumption audit | List what a human engineer would assume, and check each is stated | **Open** |
| Cold read | Someone else restates the goal and how success is judged | **Open** |
| Question probing | Write a careful contractor's questions, and check the instructions answer them | **Open** |
| Literal-compliance attack | Satisfy the instructions literally while breaking their intent | Yes, as part of red-teaming the scorer: replacing the script with a `print()` of the answer, `if True:`, a hardcoded value, a looser comparison, and deleting the broken line |
| Terminology check | The same name for the same thing in the prompt, files, and code | **Open** |
| Severity rating | Rate each sample's underspecification | Not used. With 8 similar samples and one reviewer, a rating scale adds little |
| Where the review is recorded | A spec file, the QA log, or both | Findings in [QA.md](QA.md). The traceability table is in this file |

**Traceability: instructions to scorer checks**

| Instruction | Scorer check |
|---|---|
| "Fix the error so that `python3 <script>` runs successfully" | The script exits with code 0 (else `still_broken`), within 30 seconds (else `timed_out`) |
| "Don't change what the script prints" | The output matches `expected.txt`, apart from surrounding whitespace (else `wrong_output`) |
| "Change as little as possible" | At most 3 lines differ from `broken.py` (else `rewritten`) |
| "The Python script `<script>`" | The script must still exist at that path (else `missing`) |
| "Fails with a syntax error" (the fix should repair that error, not change the logic) | No direct check. Wrong fixes that print the right output still pass (QA-004, QA-009 to QA-011) |
| "When you're done, submit" | Not scored, by design. The scorer checks the files, not the submission |

### Build-time QA

| Decision | Options to consider | Choice and reason |
|---|---|---|
| How much QA | A quick check, or a full pass with a written log | A full pass with a written log, to practice the method on a small task. The checks used are marked in the two sections above |
| Red-teaming the scorer | List wrong solutions that could pass, and test each | Yes. Write wrong fixes on purpose, check whether the scorer passes them, and log each one that does |
| Leak audit | Can the agent find the answer in the sandbox? | Yes. Check the image, the build context, and the files copied in. Also check the model provider's data terms and which files carry the canary |
| QA log | Where findings go, and their fields | [QA.md](QA.md): ID, type, severity, how found, fix, and how verified, grouped by stage |
| When QA is done | The point at which the task is ready for real runs | Tests pass and no high-severity findings are open. Open findings are listed as limitations |

| Decision | Options to consider | Choice and reason |
|---|---|---|
| What's reported | Pass rates, uncertainty, limit hits, tokens, time | Pass counts, accuracy with stderr, limit hits, errors, verdict counts, messages, time, and tokens per model. Wilson confidence intervals are **Open** |

## Run Time

### Where to run

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Location | Local machine, a codespace, or other cloud resources | A GitHub Codespace for real models |
| What runs where | Mock and reference runs locally; real models in the cloud | Locally, only `mockllm/model` and the test solvers. Real models only in the codespace |
| API keys | Where they're stored, and who can use them | Codespaces secrets only, limited to this repo. Never in a file |
| Code version | How the run machine gets the right commit | Push from the Mac, `git pull` in the codespace, check with `git log -1`. Each log records its commit |

### Models

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Which models | Providers and model versions | `anthropic/claude-haiku-5-5` and `anthropic/claude-sonnet-5-5` |
| Why these models | Capability range, cost, availability | A cheaper and a stronger model from one provider, on paid API credits |
| Generation settings | Temperature, reasoning effort, max tokens | **Default** provider settings |
| Free or paid tier | Rate limits, training on data | Paid only, because free tiers have tight rate limits and may train on prompts (QA-007) |
| Mock model | `mockllm/model` for the pipeline | Used for all local runs and tests |

### Run size

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Epochs | Runs per sample | 3, to see whether a model is consistent on the same sample |
| Samples per run | All, a subset, or one | All 8 for results |
| Smoke test | A small run before the full one | **Open:** a `--limit 2` run before each full eval |
| Repeat evals | How many full evals per model | Several per model, to see how much a single eval's numbers move |

### Concurrency and reliability

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Concurrent model calls | `--max-connections` | 2. Gentle on rate limits; the task is short anyway |
| Concurrent sandboxes | `--max-sandboxes` | **Default.** Docker sandboxes are capped at twice the CPU count |
| Retries | `--max-retries`, `--attempt-timeout` | `--attempt-timeout 180`, so a stalled model call is retried instead of hanging (QA-006). Retries: **Default** |
| Errors | `--fail-on-error` | **Default** |
| Limits set at run time | `--time-limit`, `--message-limit`, `--token-limit` | `--time-limit 600` |

### Cost

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Budget | A spend limit per eval and overall | **Open** |
| Estimate | Tokens per run from a smoke test, times runs | Tokens per eval from the logs, which `summarize_results.py` reports per model |
| Cost controls | Fewer epochs, cheaper models, caching, smaller samples | Message limit of 30, a short task, 8 samples × 3 epochs, and prompt caching |

### Before each run

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Checks | Tests pass, reference scores 1, do-nothing scores 0 | `uv run pytest tasks/fix_syntax/tests` covers all three |
| Code check | Expected commit, no uncommitted changes | `git pull` and `git log -1` in the codespace |
| Environment check | Docker running, disk, keys set | `scripts/check_model.sh` checks the API key works with one prompt |
| Run record | Where the command, commit, date, and reason are noted | The Reproduce section of [RESULTS.md](RESULTS.md#reproduce), and the eval logs themselves |

### Run-time QA

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Which transcripts to read | All, failures, a sample of passes, limit hits | All failures and limit hits |
| What to look for | Shortcuts, environment problems, unclear instructions, scorer mistakes | All four |
| Passes to check | Read some passes to catch false passes | Check the verdict and `lines_changed` for every pass. **Open:** reading a sample of pass transcripts |
| Failure review | Model's fault or the task's | Each failure goes in the failure review in [QA.md](QA.md) |
| Failure clustering | When several models fail the same way, check the spec first | Yes. A failure shared across models is checked against the spec before it's counted as a model failure |
| Verdict counts | Do the reasons match expectations? | Yes, printed by `summarize_results.py` and reported in RESULTS |
| Limit hits and errors | From the model or the setup? | Counted per model, and each one read to find its cause (QA-005, QA-006) |
| Flakiness | Do repeat runs disagree? | Compare the 3 epochs of each sample, and repeat evals of each model |
| What triggers a fix | Which findings change the task | Any finding that causes a false pass, false fail, or leak. Earlier results are rerun if the pass rule changes |

### Results

| Decision | Options to consider | Choice and reason |
|---|---|---|
| Which logs count | Latest per model, all, or a set commit | The latest full eval per model (8 samples or more). Earlier evals are kept in the [Repeat evals](RESULTS.md#repeat-evals) table |
| Where logs are kept | Local only, shared storage, or published | Local only. `logs/` is git-ignored |
| How results are built | Scripts or by hand | Scripts build `results.json` and the figures. The RESULTS tables are copied by hand (listed under Could be better) |
| What's published | Tables, figures, transcripts, logs | Tables, figures, verdict counts, and quoted transcripts. Not the raw logs |
| Comparing runs | Only runs with the same task, scorer, and settings | Only runs with the same pass rule and settings. A scorer change that changes the pass rule means rerunning |
